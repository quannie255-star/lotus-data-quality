# P11 实验报告：基于梯度的数据筛选与并行优化

> 课程：并行计算 · 选题 P11｜日期：2026-11-12
> 原始记录：`data/downstream/grad_select_bench.json`（本报告所有数字可由
> `python -m downstream.grad_select.benchmark` 复现，环境差异如实记录于 JSON `env` 块）
> 代码：`downstream/grad_select/`（core.py 串行基准 / torch_kernel.py 并行三形态 / datagen.py / benchmark.py）

## 1. 计算方法

样本 `(x, y)`，固定参数 `w`，损失 `L = ½(wᵀx − y)²`，逐样本梯度按课程附录解析式
`g = (wᵀx − y)·x`（不经自动微分）。参考集 M=64 条，先求平均梯度
`ḡref = (1/M) Σ g′ⱼ`，再为每条候选打分（余弦相似度）：

```
sᵢ = gᵢᵀḡref / (‖gᵢ‖₂ · ‖ḡref‖₂)      分母为零 → sᵢ = 0
```

按分数降序选 `k = ⌈0.05·N⌉` 条，**同分按样本编号升序**；输出全部分数与选中编号。
计算期间 w 固定不更新（各版本同一输入、同一 w）。

数据：固定种子从 U[-1,1) 生成并舍入为 FP32 值（`datagen.py`，标准库 random +
ctypes 舍入，保证串行与并行实现消费逐位相同的输入）。配置按课程参考规模：
N ∈ {1000, 10000, 50000}，M=64，d ∈ {32, 128}。

## 2. 实现版本（1 基础 + 3 并行形态）

| 版本 | 实现 | 定位 |
|---|---|---|
| serial | 纯 Python 逐样本循环，FP64 计算，零第三方依赖（`core.py`） | 基础版 / 正确性基准 |
| torch_loop | torch 向量运算 + Python 逐样本循环（`select_loop`） | 对照：证明「换库 ≠ 并行」 |
| torch_batch | 整批 (N,d) 梯度矩阵一次算完（`select_batch`） | 向量化上限 |
| torch_chunk | 4096 行分块，逐块打分后立即释放梯度（`select_chunk`） | 内存有上界的工程形态 |
| torch_batch_cuda | batch 同代码，device=cuda | GPU 臂 |

并行性来源：候选样本间相互独立（打分是逐行 map），参考梯度求平均是一次归约。
批量计算按行保留逐样本梯度——整批平均梯度不能替代逐样本梯度（课程附录明示）。

## 3. 正确性验证

- **课程官方调试用例**（w=(0,0)、参考 x=(1,0),y=-1）：四形态分数均为 `1/0/-1/0`、
  选中编号 `0`（`tests/test_grad_select.py::test_pdf_debug_case / test_torch_pdf_debug_case`）。
- **边界用例**：全部零梯度、同分按编号、N 不整除块大小（N=1001, chunk=100）全过；
  分块与整批在 FP32 下**逐位一致**（`test_chunk_equals_batch_bitwise`）。
- **并行 vs 串行全量对照**（benchmark 内嵌，随机数据五档配置）：分数最大绝对误差
  ≤ **1.5e-7**（FP32 vs FP64 舍入水平），选中编号集合**全部完全一致**
  （JSON 各臂 `correctness.selected_identical = true`）。

## 5. 结果分析

1. **torch_loop 比纯 Python 串行还慢 2~7 倍**：逐样本迭代下每次循环要付 torch 算子
   派发/小张量构造的固定开销，向量单元完全没用上——「用了并行库」不等于「做了并行
   设计」，瓶颈在 Python 级循环本身。
2. **batch 形态加速 3.6~5.9 倍**：打分变成 (N,d) 矩阵乘 + 逐行归一化，SIMD/多核
   真正吃满；d 从 32 → 128 时加速比不降反升（每行计算量变大，摊薄了框架固定开销）。
3. **chunk 与 batch 同量级、结果逐位一致**：以 4096 行为块，梯度矩阵峰值内存从
   4Nd = 25.6MB（N=50000,d=128,FP32）压到 2.1MB，代价是多次小张量操作的额外开销
   ——小 N 档 chunk 略慢于 batch，N=50000,d=32 档反而最快（×6.11，缓存局部性收益）。
   这正是课程附录「4NP 字节存储 → 分块 + 及时释放」论据的实测落点。
4. **GPU 臂没有跑赢 CPU batch**（3.4~6.8 倍，与 CPU 同量级）：本问题单条计算量
   太小（d≤128 的点积），H2D 拷贝 + kernel 启动开销吃掉了并行收益；数据规模到
   N≥10⁵~10⁶ 或 d≥10³（真实模型梯度维度是 10⁶~10⁸ 级）GPU 才能拉开差距——
   扩展版（LoRA 梯度筛选，见 §7）正是这个 regime。
5. **线程扫描平坦且 1 线程快过默认 24 线程**：0.2 秒量级的负载下，24 线程的同步/
   调度开销超过并行收益（0.2151s → 单线程 0.1687s）。多线程加速需要「计算量/线程
   管理开销」足够大；本配置 N·d ≤ 6.4×10⁶ FLOP 级，属于开销敏感区。
6. **误差水平**：并行版 FP32 vs 串行 FP64 的分数差 ≤1.5e-7（float32 机器精度
   6×10⁻⁸ 的 2~3 倍，来自点积累加顺序差异），未观察到任何选中集合翻转。

## 6. 存储开销实测口径

FP32 下保存全部候选梯度需 4Nd 字节：N=50000, d=128 → 25.6MB（线性模型可整批驻留）；
换成 Qwen3-0.6B decoder 全参数梯度（P≈4.4×10⁸）则单条 1.76GB、一万条 17.6TB
（课程附录数字）——这就是扩展版必须「只对 LoRA 低秩参数求导 + 打分后立即释放」的原因。

## 7. 扩展内容（选做，与数据治理项目联动）——已实跑

同一套打分/筛选口径已接入 Lotus 数据治理项目（`downstream/lora_finetune/`）：
Qwen3-0.6B + LoRA（r=8，只训低秩适配器），warm-up 1%×1 epoch 得锚点 φ0 → 对 2,396 篇
真实治理语料逐条 backward 取 LoRA 梯度打分（全量打分 GPU 墙钟 799~2053s，随 laptop
GPU 热状态波动；**分数值**跨运行 6 位小数确定一致，即课程附录「模型梯度」regime 的
逐条 backward + 打分后释放策略实测）→ top-5%（120 篇）、随机 5%（120 篇）、全量
（2,396 篇）三臂 SFT（超参严格一致，唯一变量=训练文档集）→ 独立测试集（536 行，
SHA-256 防泄漏剔除 6 条重叠）对比 token 级 ppl。

超参敏感性对照（grad top-5% vs random 5%，原始记录 `lora_report*.json`）：

| SFT 配置 | 筛选臂 ppl | 随机臂 ppl | 筛选 vs 随机 |
|---|---|---|---|
| lr=2e-4 × 4ep | 35.36 | 38.69 | **−8.61%（筛选臂好）** |
| lr=1e-4 × 3ep | 24.10 | 23.77 | +1.41%（噪声区间） |
| lr=5e-5 × 2ep | 21.67 | 21.35 | +1.51%（噪声区间） |

三臂对照（lr5e-5×2ep 生产配置，`lora_report_lr5e5ep2_3arm.json`，基线 φ0=23.51）：

| 臂 | 训练文档 | test ppl | vs 基线 | vs 全量 |
|---|---|---|---|---|
| grad_arm（top-5%） | 120 | 21.671 | −7.82% | +15.24% |
| random_arm（随机 5%） | 120 | 21.349 | −9.19% | +13.53% |
| **full_arm（全量）** | 2,396 | **18.805** | **−20.01%** | — |

诚实结论：
1. **治理语料的下游收益成立且强**——全量 SFT 使 test ppl 降 **20%**（因果链终证成立）。
2. **梯度筛选的优势只在强微调（遗忘）区间稳健**——lr2e-4×4ep 时选对数据减轻损伤 8.6%；
   温和区间 grad≈random（±1.5% 属单 seed 噪声），不声称筛选普遍优于随机。
3. **top-5% 选择未能在本配置逼近全量**——全量（18.81）显著优于任一 5% 子集（~21.5），
   5% 选择是有损的（省 95% 数据、ppl 高约 15%）。这如实回答课程「筛选是否有助于微调」：
   在语料小、全量训练可负担时，**用全部治理语料胜过选子集**；数据选择的收益要在
   「全量负担不起」或「强微调致遗忘」时才显现（后者本实验已证）。
4. 若只报 lr2e-4×4ep 单配置或只报 5% 两臂，都会得出片面结论——三配置 × 三臂矩阵
   正是为防「挑口径」（quantitative-claim-audit 纪律）。
跨运行确定性：打分中位数 0.115816 在多次独立运行 6 位小数一致（含缓存复用），
grad/random 臂 ppl 在独立跑与三臂跑中逐位一致（21.671/21.349）。
详见 `downstream/lora_finetune/`（README/DESIGN/口径说明/开发日志）。
